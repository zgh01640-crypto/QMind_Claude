# QMind AI Harness 约束、规则与知识库盘点

> 盘点日期：2026-08-02
> 盘点范围：QMind 当前代码仓库，重点关注“单条组价 / 批量组价”主链路，同时标注旧版及次级链路。
> 结论：系统已经形成“代码硬约束 + 造价业务规则 + 版本化结构化知识库 + 人工反馈库”四层领域 AI Harness。

## 1. 总体结构

当前组价 Harness 的运行关系如下：

```text
工程量清单
  ↓
固定工作流编排
  ├─ 编码核查
  ├─ 项目特征分析与默认值补全
  ├─ 定额候选检索
  ├─ AI 套定额与结构化提交
  ├─ 人工组价对比评测
  ├─ 组合定额换算
  └─ 系数换算
  ↓
候选白名单、Tool Schema、后端归一化
  ↓
人工确认 / 拒绝 / 换算确认
  ↓
运行记录、准确率指标和明细报告
```

当前主链路不是开放式 ReAct Agent，而是“确定性 Workflow Agent + 局部 LLM Tool Calling + DB Retrieval”。模型只在需要专业判断的节点工作，不能自行改变流程或任意访问知识库。

## 2. 当前 Harness 的运行时约束

### 2.1 固定七步工作流

当前实际代码中的主链路包含七个步骤：

| 步骤 | 名称 | 执行方式 | 主要输出 |
|---|---|---|---|
| 1 | 编码核查 | 确定性数据库查询 | 标准名称、是否一致 |
| 2 | 项目特征 | LLM + Tool Calling + 后端校验 | 完整性、缺失特征、补全结果 |
| 3 | 定额候选 | 确定性数据库查询 | 候选定额集合 |
| 4 | 套定额结果 | LLM 分析 + 强制结构化提交 | 定额、系数、置信度、理由 |
| 5 | 人工对比 | 确定性规则 | 命中、遗漏、额外 |
| 6 | 组合换算 | LLM 判断 + 后端公式计算 | 组合定额及次数建议 |
| 7 | 系数换算 | LLM 判断 + 规则解析 | 系数、作用对象、复核要求 |

每一步均可保存阶段结果和耗时，核心实现位于：

- `api/routers/pricing_task.py::_stream_pricing_item`
- `pricing_task_runs.step_timings`
- `pricing_task_batch_item_runs.step_timings`

### 2.2 候选白名单

AI 只能从后端返回的候选定额中选择：

1. Tool Schema 明确禁止提交候选外定额。
2. 输出后端再次按 `(dekid, dezmid)` 与候选集合比对。
3. 候选集合中不存在的结果直接丢弃。
4. 重复定额自动去重。
5. 置信度限制为 `high`、`medium`、`low`。

这是当前系统最主要的防幻觉约束。

相关实现：

- `api/routers/pricing_task.py::_TOOL_SUBMIT_QUOTA_MATCH`
- `api/routers/pricing_task.py::_normalize_matches`

### 2.3 清单编码约束

清单编码在检索前会进行标准化：

- 去掉首尾及编码内部空格；
- 编码长度大于 9 位时去掉末 3 位项目流水码；
- 使用处理后的基础编码查询标准清单和定额映射。

当前编码与名称不一致只会产生提示，尚不会阻断后续组价流程。

相关实现：`api/routers/pricing_task.py::_base_code`、`exec_check_item_code`。

### 2.4 项目特征补全约束

当项目特征包含“综合考虑”时：

- AI 只能从 `tqdk_tzhkl` 返回的默认值候选中选择；
- 只能补全明确匹配的 `feature_name/default_value`；
- 不得覆盖已经存在的明确特征值；
- 无法明确匹配时不得补全；
- LLM 输出后由后端再次验证默认值是否属于候选集合；
- 符合条件时可将规范化描述回写到 `boq_items.item_description`。

相关实现：

- `api/routers/pricing_task.py::_load_feature_default_candidates`
- `api/routers/pricing_task.py::_normalize_feature_analysis_result`
- `api/routers/pricing_task.py::_TOOL_SUBMIT_FEATURE_ANALYSIS`

### 2.5 强制结构化输出

当前主链路定义了四类关键提交工具：

| Tool | 功能 | 主要约束 |
|---|---|---|
| `submit_feature_analysis` | 特征完整性分析 | 必填完整性、缺失项、规范化描述和默认值来源 |
| `submit_quota_match` | 套定额结果 | 只能提交候选 ID，限制置信度枚举 |
| `submit_conversion_check` | 组合定额换算 | 逐条覆盖规则，不修改已确认定额和原工程量系数 |
| `submit_coefficient_check` | 系数换算 | 逐条覆盖系数规则，限制作用资源类型 |

Tool Schema 使用必填字段、枚举、类型校验和 `additionalProperties: false` 控制输出边界。模型输出还会经过后端归一化，模型不是最终数据权威。

### 2.6 知识库版本约束

任务、单条 Run 和批量 Run 均绑定 `kb_version_id`：

- 未指定时使用已经发布的 active 版本；
- 只允许选择 `validated`、`active`、`retired` 版本；
- 执行期间不会因新版本发布而自动切换数据；
- 查询通过 `pricing_kb_data_version()` 找到该发布版本对应的数据表版本。

知识库生命周期：

```text
importing → validated → active → retired
                    ↘ failed
```

相关实现：

- `db/pricing_kb_versions.py`
- `db/schema_pricing_kb_versions.sql`
- `db/schema_pricing_kb_import_admin.sql`

注意：项目特征默认值表 `tqdk_tzhkl` 当前没有 `kb_version_id`，尚未完全纳入主知识库的版本治理体系。

### 2.7 人工确认闸门

AI 输出不能直接成为最终业务结果：

- 初始结果以待确认状态保存；
- 用户可以调整定额后确认；
- 确认时再次验证定额是否存在于 Run 绑定的知识版本；
- 用户可以拒绝整个 Run；
- 只有已确认 Run 才能执行组合换算；
- 换算结果需要再次确认才能写回；
- 最终确认的工程量系数必须大于 0。

相关接口：

- `POST /pricing-task-runs/{run_id}/confirm`
- `POST /pricing-task-runs/{run_id}/conversion-confirm`
- `POST /pricing-task-runs/{run_id}/reject`

### 2.8 模型调用与失败约束

当前模型运行参数及故障策略：

- 使用 OpenAI-compatible SDK 调用 DeepSeek；
- 模型名称由 `DEEPSEEK_MODEL` 配置；
- 默认模型为 `deepseek-v4-pro`；
- 默认请求超时 120 秒；
- 启用高强度推理和流式输出；
- 单阶段最多尝试两次；
- 失败局限在当前阶段；
- SSE 实时输出推理、阶段结果和错误；
- Run 保存错误信息及完成状态。

当前尚无指数退避、熔断、备用模型路由和按错误类型分类的重试策略。

## 3. 当前实际生效的业务规则

### 3.1 套定额基本规则

当前主系统提示词规定：

- 模型角色为建筑工程造价工程师；
- 必须基于后端候选定额选择；
- 不得编造候选外定额；
- 工程量系数只表示清单量和定额单位之间的纯换算关系；
- `high` 表示特征充分匹配；
- `medium` 表示主要特征匹配但存在疑问；
- `low` 表示关键特征缺失；
- 全程使用中文分析。

当前新版 `pricing_task` 的系统提示词硬编码在 `build_system_prompt()` 中，后台的 `prompt_templates` 暂不控制该主链路。

### 3.2 清单到定额候选映射

当前候选生成主要依赖结构化关系库：

```text
清单基础编码
  ↓
TQDK_TQDZM：标准清单子目
  ↓
TQDK_TQDZY：清单—定额关联关系
  ↓
TDEK_TDEZM：定额子目
```

附加规则：

- 可通过 `quota_library_ids` 限定候选定额库；
- 单次最多返回 80 条候选；
- 定额章节、工作内容和单位一并提供给模型判断；
- 无候选时不进入套定额模型选择。

因此当前候选机制属于 `DB Mapping Retrieval + LLM Ranking`，并非向量语义 RAG。

### 3.3 组合定额换算规则

组合定额规则只允许来自 `TDEK_TZHHS`：

1. 每条已确认定额可以有 0 至多条组合规则。
2. 每条规则必须单独判断，不允许合并。
3. 只判断项目特征中的数量特征是否命中规则。
4. AI 负责判断是否匹配并抽取特征值。
5. 后端按固定公式计算组合次数：

```text
组合次数 = (项目特征值 - 基础值 jcz) / 增减单位 zjdw
```

6. 计算结果为负数时截断为 0。
7. 缺少特征值、单位不一致或 `zjdw` 无效时转人工复核。
8. 费用为 0 的说明型组合规则仍需展示，但不得臆造工料机调整。
9. 该步骤只提供组合次数建议，不允许修改已确认定额。

### 3.4 系数换算规则

系数规则只允许来自 `TDEK_TZNHS.hssm`：

- 从“系数 1.2”等说明中解析系数；
- “子目乘以系数”作用于全部工料机；
- 包含“人工”时作用于人工；
- 包含“材料”时作用于材料；
- 包含“机械”时作用于机械；
- AI 必须覆盖输入中的每条定额和每条系数规则；
- `rule_index` 必须保持一致；
- 当前只保存、解释和展示系数，不自动改写工料机含量。

### 3.5 人工对比评测规则

系统按完整清单编码查找人工组价结果，并计算：

- 命中定额；
- 遗漏定额；
- 额外定额；
- 人工定额数；
- AI 定额数；
- 命中率；
- 完全一致清单数。

人工编码可能带有“换”等后缀，因此当前使用包含关系判断。例如 AI 编码 `010001-32` 可以命中人工编码 `010001-32换`。

相关实现：`api/routers/pricing_task.py::_manual_quotas`、`_evaluate`。

## 4. 当前主知识库

### 4.1 组价知识库

主要源文件：`mydoc/智能组价系统库.db`。

源 SQLite 文件包含 9 张核心表：

| 表 | 内容 | 当前源文件记录数 |
|---|---|---:|
| `TLibs` | 清单库、定额库目录 | 15 |
| `TQDK_TZJMC` | 清单库章节目录 | 610 |
| `TDEK_TZJMC` | 定额库章节目录及说明 | 5,590 |
| `TQDK_TQDZM` | 标准工程量清单子目 | 4,372 |
| `TDEK_TDEZM` | 定额子目、单位、工作内容和价格构成 | 32,997 |
| `TQDK_TQDZY` | 清单与定额候选映射 | 26,298 |
| `TDEK_TZMGC` | 定额工料机组成和消耗量 | 332,382 |
| `TDEK_TZHHS` | 组合定额增减换算规则 | 1,525 |
| `TDEK_TZNHS` | 定额系数换算说明 | 66,351 |

表结构定义：`db/schema_pricing_kb_original.sql`。

#### 源文件重复情况

以下文件 SHA-256 完全一致：

- `mydoc/智能组价系统库.db`
- `mydoc/rule/智能组价系统库.db`
- `mydoc/rule/智能组价系统库（最新）.db`

`mydoc/rule/智能组价系统库（全）.db` 是另一份不同数据文件。系统应以 PostgreSQL 中已发布的 active version 为运行权威，不能只根据文件名中的“最新”判断版本。

### 4.2 项目特征默认值库

源文件：`mydoc/rule/01土建专业特征默认值-（第1版）6.18.xlsx`。

当前源文件解析情况：

- 3,250 条源记录；
- 覆盖 628 个清单编码；
- 解析过程记录 628 条问题或提示。

运行时表：`tqdk_tzhkl`。

主要字段：

- 清单库 ID；
- 清单子目 ID；
- 清单编码和名称；
- 章节名称；
- 特征名；
- 原特征值；
- 默认值；
- 源文件哈希、Sheet 和行号。

该知识库目前只用于处理“综合考虑”默认值，不是完整的项目特征本体或知识图谱。

### 4.3 人工组价对照库

人工组价知识由以下表组成：

- `manual_boq_projects`
- `manual_boq_sections`
- `manual_boq_items`
- `manual_boq_quotas`

主要用途：

1. 为 AI 套定额提供人工标准答案；
2. 计算命中、遗漏、额外和准确率；
3. 生成任务级准确率报告；
4. 作为未来离线评测集和 golden set 的数据基础。

### 4.4 执行记录与反馈知识

系统持久化以下运行数据：

- 编码核查结果；
- 项目特征分析；
- 候选定额集合；
- AI 套定额结果；
- 人工对比评测；
- 组合换算结果；
- 系数换算结果；
- 分步骤耗时；
- 推理文本；
- 错误信息；
- 确认、拒绝和换算确认结果。

核心运行表：

- `pricing_tasks`
- `pricing_task_runs`
- `pricing_task_results`
- `pricing_task_batches`
- `pricing_task_batch_item_runs`

这些数据当前主要用于展示、复核和报告，尚未自动回流为新的清单—定额映射或业务规则。

## 7. 当前约束缺口和风险

### 7.1 部分软约束没有升级为业务闸门

- 编码名称不一致仍可继续运行；
- 项目特征不完整仍可继续匹配；
- 特征不完整不会自动强制降为低置信度；
- AI 初次给出的 `qty_factor` 在归一化阶段没有强制大于 0，只有换算确认时进行了正数校验。

### 7.2 知识版本没有完全统一

- 九张核心组价表已经纳入 `kb_version_id`；
- `tqdk_tzhkl` 默认值表没有版本绑定；
- 人工组价数据没有 golden-set 版本；
- Prompt 也没有随 Run 保存版本号。

因此目前还无法严格复现“某次运行所使用的全部知识和规则快照”。

### 7.3 规则资料与可执行规则存在差距

Word、Excel 和 Markdown 中的专家规则很多，但只有写入数据库表、Prompt 或 Python 规则函数的部分才会在运行时生效。文件存在不等于已经成为 Harness 知识。

### 7.4 当前评测属于业务对比，不是完整离线 Evals

现有人工对比能够计算命中率，但尚缺少：

- 固定且版本化的测试集；
- 分专业、分章节、分清单类型指标；
- 候选召回率和最终选择准确率拆分；
- Prompt/模型/知识版本之间的对照实验；
- 发布前自动回归门槛。

### 7.5 可观测性仍不完整

系统已有阶段结果、耗时、错误和推理文本，但尚缺统一的：

- Trace ID / Span；
- 模型请求 ID；
- Prompt 版本；
- 模型实际版本；
- 输入输出 Token；
- 缓存命中情况；
- 单次及任务级成本；
- 每阶段重试次数和错误类型。

## 8. 建议的知识与规则治理目录

后续可将当前资产统一整理为以下逻辑结构：

```text
Harness 资产
├─ Constraints（硬约束）
│  ├─ 工作流状态机
│  ├─ Tool Schema
│  ├─ 候选白名单
│  ├─ 状态迁移
│  └─ 人工确认闸门
├─ Rules（可执行规则）
│  ├─ 编码规则
│  ├─ 特征默认值规则
│  ├─ 清单—定额映射规则
│  ├─ 组合定额规则
```

## 9. 最终盘点结论

当前有效的 QMind Harness 可以概括为：

```text
硬约束
├─ 固定七步编排
├─ 候选白名单
├─ 严格 Tool Schema
├─ 后端归一化
├─ 知识库版本锁定
└─ 人工确认闸门

业务规则
├─ 编码标准化
├─ “综合考虑”默认值补全
├─ 清单—定额映射
├─ 组合定额次数计算
├─ 工料机系数作用范围
└─ 人工结果命中评测

知识库
├─ 九张核心组价知识表
├─ 项目特征默认值库
├─ 人工组价对照库
├─ BS2024 标准库
├─ 信息价和参考价库
└─ Run 执行与反馈数据
```

系统已经具备领域 AI Harness 的主体，但“文档规则可执行化、知识版本统一、Prompt/模型可追溯、反馈自动沉淀、离线评测门禁”仍是下一阶段建设重点。
